檔案上傳測試案例，附上執行它們的檔案

一份檔案上傳測試案例的檢查表，從大小限制到試圖離開所在資料夾的檔名。每個案例都寫明測試它的檔案，以及你的系統應如何處理該檔案，所以這份列表不只能讀，還能直接執行。

一道指令產生整份列表

tfg generate --preset upload-validation --limit 10mb --allow jpg,png,pdf --out ./upload 會為下面幾乎每個案例寫出一個檔案，並附上一份清單，說明每個檔案應該得到什麼結果。把限制和類型換成你的表單宣告的值。

accept 表示你的系統應該接受該檔案，reject 表示應該拒絕它並給出清楚的訊息。unspecified 表示兩種答案都可能正確，所以請寫下你的系統採用哪一種，並檢查它每次都這樣做。結果後面的詞是清單給出的原因。

大小

大小限制是否在宣告的位置生效？

測試案例檔案預期
比限制小一個位元組10mb_under_1b.jpgaccept
恰好等於限制10mb_at_limit.jpgaccept
比限制大一個位元組10mb_over_1b.jpgreject size_limit
限制的兩倍，用來確認伺服器會提早停止讀取，而不是全部讀進記憶體10mb_far_over_2x.jpgreject size_limit
0 位元組的空檔案empty.jpgunspecified size_zero

限制最常出錯的兩種情況是：只在瀏覽器中檢查的限制，以及以 MB 宣告、程式碼卻以 MiB 計算的限制。size-boundaries 預設集會在你選定的限制周圍的每個距離上各放一個檔案，即兩側各相差一個位元組、一個千位元組和一個百萬位元組。

類型

表單是否接受該接受的類型，並拒絕其餘類型？

測試案例檔案預期
表單接受的每種類型，各用一個該類型的真實檔案allowed_jpg.jpg、allowed_png.png、allowed_pdf.pdfaccept
表單不接受的類型denied.svg、denied.html、denied.exe、denied.shreject extension_rule
副檔名是一種類型，內容卻是另一種，例如命名為 .jpg 的 PDFpdf_as_jpg.jpg、png_as_pdf.pdf、jpg_as_png.pngreject mime_mismatch
兩個副檔名，最後一個不被允許invoice.jpg.exereject extension_rule
完全沒有副檔名invoiceunspecified extension_rule
大寫的副檔名PHOTO.JPGunspecified extension_rule

被當作圖片或純文字接受的 SVG 或 HTML 檔案，是讓指令碼繞過表單的一種辦法。所以除非你的表單本來就要接受它們，否則它們都在應拒絕的類型列表中。

內容

系統是開啟檔案，還是只看檔名？

測試案例檔案預期
被截短的檔案，就像中斷的上傳留下的那樣corrupt-truncate.pdfreject content_malformed
開頭位元組是零的檔案，因此沒有任何資訊說明它是什麼corrupt-zero-head.pngreject content_malformed
格式允許的最小檔案，合法且極小tfg generate --preset empty-and-minimalaccept

一個只有名稱和大小正確的檔案，能通過所有不開啟它的檢查。損毀的範例檔案有 PDF、Word、Excel、PowerPoint、JPG、PNG、MP4 和 ZIP 格式，損毀的測試檔案說明如何以任意格式、任意大小製作它們。

檔名

檔案取回時還是原來的名稱嗎？

測試案例檔案預期
空格和括號my report (final) v2.jpgaccept
非 ASCII 字母和 emojiwiadomość_日本語_🎉.jpgunspecified filename_invalid
超過 200 個字元的檔名aaa...aaa.jpgunspecified filename_too_long
用 ../ 或 ..\ 跳出所在資料夾的檔名climbing_name.jpg，以 ../tfg_climbed_out.jpg 的名稱上傳unspecified filename_traversal
Linux 或 Windows 上的絕對路徑absolute_name.jpg，以 /tmp/tfg_climbed_out.jpg 的名稱上傳unspecified filename_traversal

帶有路徑的名稱無法儲存到磁碟上，所以檔案本身用普通的名稱，清單會說明上傳時用什麼名稱。接受檔案並只保留名稱的最後一部分，是好的處理方式。把它寫到上傳資料夾之外，正是這個案例要找出的缺陷。filename-handling 預設集還有更多檔名：形似的字母、不可見字元、Windows 保留的名稱，以及以位元組計算的長度。

數量與壓縮檔

檔案很多，或一個檔案裡裝著很多檔案時，會發生什麼？

測試案例檔案預期
一次上傳 50 個檔案bulk_0001.jpg 到 bulk_0050.jpgaccept
真正包含 200 份文件的 ZIPtfg generate --format zip --size 5mb --set entries=200 --set entry_format=pdfaccept
你的系統會解壓縮的壓縮檔，先檢查 zip slip 和 zip 炸彈tfg tool archive-scan upload.zip安全，或列出發現的問題

--bulk 設定大量上傳包含多少個檔案，最多一萬個。工具說明壓縮檔檢查會尋找什麼。

在測試中

把列表當作測試執行

清單包含每個檔案的預期結果和上傳時使用的名稱，所以一個迴圈就能跑完整份列表： 

import json, os

directory = "upload"
manifest = json.load(open(os.path.join(directory, "manifest.json")))

for entry in manifest["files"]:
    outcome = entry["expected"]["outcome"]
    if outcome == "unspecified":
        continue
    name = entry.get("send_as", entry["name"])
    response = upload(os.path.join(directory, entry["path"]), name)
    assert response.ok == (outcome == "accept"), name

標為 unspecified 的檔案在這裡被略過，因為它們的答案取決於你自己的策略。決定策略，用 expected 寫進配方，迴圈就會一併檢查它們。CI 中的測試檔案會在流程中執行這段程式碼。
