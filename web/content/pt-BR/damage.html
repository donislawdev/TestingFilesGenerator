Como criar um arquivo corrompido para testes

Um validador que só viu arquivos saudáveis não foi realmente testado. Veja como obter um arquivo quebrado de propósito, que sai com exatamente o tamanho que você pede e traz um manifesto dizendo o que o seu sistema deve fazer com ele.

A resposta curta

tfg generate --format png --size 2mb --damage zero-head --out ./out grava um PNG de exatamente 2097152 bytes cujos primeiros bytes são zeros, e o manifesto ao lado registra que o seu sistema deve rejeitá-lo.

O jeito de sempre

Por que um arquivo corrompido à mão é um teste ruim

O jeito de sempre é um editor hexadecimal, um script que troca alguns bytes aleatórios ou cortar um arquivo com head ou truncate. Funciona uma vez, e depois sai caro:

  • É diferente a cada vez. Um byte aleatório cai num lugar novo a cada execução, então uma falha de terça pode não voltar na quarta.
  • Muda o tamanho. Um arquivo cortado fica menor que o limite abaixo do qual deveria ficar, então a checagem de tamanho responde antes da checagem de conteúdo e o teste passa pelo motivo errado.
  • Muitas vezes passa despercebido. Texto simples continua legível com um byte alterado no meio, e um leitor de imagens tolerante simplesmente o desenha, então o arquivo que deveria estar quebrado é aceito.
  • Não diz nada sobre o que deve acontecer. O arquivo é só bytes, e quem ler o teste depois precisa adivinhar se a intenção era aceitação ou rejeição.

O que você recebe

Um arquivo danificado continua com o tamanho que você pediu

O arquivo é gerado normalmente e quebrado depois, a caminho do disco. Ele mantém o tamanho pedido, e o mesmo comando grava os mesmos bytes outra vez. 

tfg generate --format png --size 2mb --damage zero-head --out ./out
tfg generate --format pdf --size 1mb --count 5 --damage zero-head:bytes=16 --out ./broken
tfg generate --format zip --size 5mb --damage truncate:missing=30 --out ./cut
tfg generate --format jpg --size 500kb --damage append-junk --out ./tail

As configurações vão depois de dois-pontos. A opção pode ser repetida, e os danos são aplicados na ordem em que você os escreve. Funciona com cada um dos {{ .Facts.FormatCount }} formatos.

zero-head grava zeros sobre o início do arquivo. A maioria dos leitores olha ali primeiro, para a assinatura e o cabeçalho que dizem o que o arquivo é, então quase todo leitor percebe. Texto simples e logs não têm assinatura e também são recusados, porque uma sequência de bytes zero não é texto. Abaixo de quatro bytes, alguns formatos saem com um dano de que nenhum leitor reclama, e por isso a configuração começa em quatro.

truncate corta o fim do arquivo, como um upload ou uma cópia interrompidos o deixam, e o arquivo continua com o tamanho que você pediu: ele é gerado maior e só o seu início chega ao disco. missing diz que parte do arquivo inteiro some, metade se você não disser outra coisa.

append-junk grava bytes aleatórios depois do fim do arquivo, 64 se você não disser outra coisa, como chega um arquivo com algo grudado no fim. O mesmo comando acrescenta os mesmos bytes.

O que o manifesto diz

Um manifesto que diz o que deve acontecer

Onde o dano quebra as regras do formato, a entrada diz que o seu sistema deve rejeitá-lo, com o dano registrado ao lado: 

"expected": {
  "outcome": "reject",
  "reason": "content_malformed",
  "confidence": "certain"
},
"damage": [
  {
    "type": "zero-head",
    "settings": {
      "bytes": "8"
    }
  }
]

Onde os leitores divergem, a entrada diz isso em vez de adivinhar. Um arquivo de texto cortado continua sendo texto, e a maioria dos visualizadores ignora bytes depois do fim de um PNG, então a entrada deixa a resposta para o seu sistema, oferece as duas e diz por quê: 

"expected": {
  "outcome": "unspecified",
  "reason": "content_malformed",
  "detail": "A PNG ends at its IEND chunk and most viewers skip what follows it.",
  "confidence": "policy_dependent",
  "policy_options": ["accept", "reject"]
}

tfg damage <id> lista os formatos em que um dano deixa a resposta para o seu sistema, e por quê.

Quatro pedidos são recusados antes de qualquer coisa ser gravada, porque cada um deixaria no disco um arquivo que o manifesto descreve errado:

  • um arquivo menor do que o dano precisa, que sairia intacto
  • expected: accept ao lado de um dano que quebra as regras do formato, porque nada que as siga aceita o arquivo. Onde a resposta depende do seu sistema, accept é permitido. Escreva sanitize se o seu sistema deve consertar o arquivo, ou unspecified se essa é justamente a pergunta que você faz
  • truncate depois de append-junk, porque cortaria os bytes acrescentados. Coloque truncate primeiro
  • truncate ou append-junk em um arquivo compactado que tira o tamanho do que contém, porque não há um tamanho de onde partir

Em uma receita

Arquivos saudáveis e quebrados em uma execução

Ponha os dois em uma receita, e o manifesto leva a expectativa de cada arquivo, então o teste não precisa de uma lista de qual é qual: 

version: 1
targets:
  - id: healthy
    format: pdf
    size: 1mb
    expected: accept
  - id: broken
    format: pdf
    size: 1mb
    damage:
      - zero-head

Em um teste

Transformando em um teste

O teste lê o manifesto e confere se o que aconteceu é o que foi declarado. Não precisa de uma lista de nomes de arquivo: 

import json, os

directory = "healthy-and-broken"
manifest = json.load(open(os.path.join(directory, "manifest.json")))

for entry in manifest["files"]:
    outcome = entry["expected"]["outcome"]
    if outcome == "unspecified":
        continue
    response = upload(os.path.join(directory, entry["path"]))
    if outcome == "reject":
        assert not response.ok
    else:
        assert response.ok

Um arquivo cujo resultado é unspecified fica de fora aqui, porque o que o seu sistema deve fazer com ele é a sua própria política. A entrada dele diz por quê, e policy_options lista as respostas possíveis.

Uma boa recusa é uma recusa limpa. Uma mensagem que diz o que estava errado é a resposta que você quer. Um erro de servidor, uma trava ou um arquivo salvo pela metade é o defeito que este teste existe para achar.
