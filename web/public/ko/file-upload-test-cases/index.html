활용 사례

파일 업로드 테스트 케이스와 실행할 파일

크기 한도부터 자기 폴더 밖으로 나가려는 파일 이름까지, 파일 업로드를 위한 테스트 케이스 체크리스트입니다. 케이스마다 그것을 테스트하는 파일과 시스템이 그 파일로 해야 할 일이 적혀 있어서, 읽기만 하는 목록이 아니라 실행할 수 있는 목록입니다.

명령 하나로 전체 목록을

tfg generate --preset upload-validation --limit 10mb --allow jpg,png,pdf --out ./upload는 아래 거의 모든 케이스의 파일을, 각 파일에 무슨 일이 일어나야 하는지 알려 주는 매니페스트와 함께 씁니다. 한도와 유형에는 업로드 양식이 선언한 값을 넣으세요.

accept는 시스템이 파일을 받아야 한다는 뜻이고, reject는 명확한 메시지와 함께 거부해야 한다는 뜻입니다. unspecified는 어느 답이든 맞을 수 있다는 뜻이므로, 시스템이 어느 쪽을 의도하는지 적어 두고 매번 그렇게 동작하는지 확인하세요. 결과 뒤의 단어는 매니페스트가 제시하는 이유입니다.

크기

크기 한도가 선언한 지점에서 적용되나요?

테스트 케이스파일기대 결과
한도보다 1바이트 작음10mb_under_1b.jpgaccept
정확히 한도10mb_at_limit.jpgaccept
한도보다 1바이트 큼10mb_over_1b.jpgreject size_limit
한도의 두 배. 서버가 전부 메모리에 담지 않고 일찍 읽기를 멈추는지 확인합니다10mb_far_over_2x.jpgreject size_limit
0바이트의 빈 파일empty.jpgunspecified size_zero

한도가 가장 자주 틀리는 경우는 두 가지입니다. 브라우저에서만 검사하는 한도, 그리고 MB로 정한 한도를 코드가 MiB로 세는 경우입니다. size-boundaries 프리셋은 고른 한도에서 모든 거리, 즉 양쪽으로 1바이트, 1킬로바이트, 1메가바이트 떨어진 곳에 파일을 둡니다.

유형

양식이 받아야 할 유형은 받고 나머지는 거부하나요?

테스트 케이스파일기대 결과
양식이 받는 각 유형을 해당 유형의 실제 파일로allowed_jpg.jpg, allowed_png.png, allowed_pdf.pdfaccept
양식이 받지 않는 유형denied.svg, denied.html, denied.exe, denied.shreject extension_rule
확장자는 한 유형인데 내용은 다른 유형, 예를 들어 .jpg라는 이름의 PDFpdf_as_jpg.jpg, png_as_pdf.pdf, jpg_as_png.pngreject mime_mismatch
확장자가 두 개이고 마지막 것이 허용되지 않음invoice.jpg.exereject extension_rule
확장자가 아예 없음invoiceunspecified extension_rule
대문자 확장자PHOTO.JPGunspecified extension_rule

이미지나 일반 텍스트로 받아들여진 SVG나 HTML 파일은 스크립트가 양식을 통과하는 방법이 됩니다. 그래서 양식이 일부러 받으려는 것이 아니라면 거부할 유형 목록에 들어 있습니다.

내용

시스템이 파일을 열어 보나요, 아니면 이름만 보나요?

테스트 케이스파일기대 결과
중간에 끊긴 업로드가 남기는 것처럼 짧게 잘린 파일corrupt-truncate.pdfreject content_malformed
첫 바이트들이 0이라서 무엇인지 알려 주는 것이 없는 파일corrupt-zero-head.pngreject content_malformed
형식이 허용하는 가장 작은 파일, 유효하고 아주 작은 파일tfg generate --preset empty-and-minimalaccept

이름과 크기만 맞는 파일은 파일을 열어 보지 않는 모든 검사를 통과합니다. 손상된 샘플 파일은 PDF, Word, Excel, PowerPoint, JPG, PNG, MP4, ZIP으로 준비되어 있고, 손상된 테스트 파일에서 어떤 형식, 어떤 크기로든 만드는 방법을 설명합니다.

이름

파일이 받은 이름 그대로 돌아오나요?

테스트 케이스파일기대 결과
공백과 괄호my report (final) v2.jpgaccept
ASCII 이외의 문자와 이모지wiadomość_日本語_🎉.jpgunspecified filename_invalid
200자가 넘는 이름aaa...aaa.jpgunspecified filename_too_long
../ 또는 ..\로 폴더 밖으로 나가는 이름climbing_name.jpg, ../tfg_climbed_out.jpg라는 이름으로 업로드unspecified filename_traversal
Linux 또는 Windows의 절대 경로absolute_name.jpg, /tmp/tfg_climbed_out.jpg라는 이름으로 업로드unspecified filename_traversal

경로가 든 이름은 디스크에 저장할 수 없으므로, 파일은 평범한 이름을 갖고 어떤 이름으로 업로드할지는 매니페스트가 알려 줍니다. 파일을 받고 이름의 마지막 부분만 남기는 것은 좋은 답입니다. 업로드 폴더 밖에 쓰는 것이 바로 이 케이스가 찾으려는 결함입니다. filename-handling 프리셋에는 훨씬 더 많은 이름이 있습니다. 비슷하게 생긴 글자, 보이지 않는 문자, Windows가 예약한 이름, 바이트로 세는 길이 등입니다.

양과 아카이브

파일이 많거나 파일 하나에 많은 파일이 들어 있으면 어떻게 되나요?

테스트 케이스파일기대 결과
한 번의 업로드에 파일 50개bulk_0001.jpg부터 bulk_0050.jpg까지accept
실제로 문서 200개가 든 ZIPtfg generate --format zip --size 5mb --set entries=200 --set entry_format=pdfaccept
시스템이 압축을 푸는 아카이브, 먼저 zip slip과 zip 폭탄을 검사tfg tool archive-scan upload.zip안전함, 또는 발견한 내용

--bulk는 대량 업로드에 담을 파일 수를 최대 1만 개까지 정합니다. 아카이브 검사가 무엇을 찾는지는 도구에서 설명합니다.

테스트에서

목록을 테스트로 실행하기

매니페스트에는 모든 파일의 기대 결과와 업로드할 때 쓸 이름이 있으므로, 반복문 하나로 전체 목록을 실행합니다. 

import json, os

directory = "upload"
manifest = json.load(open(os.path.join(directory, "manifest.json")))

for entry in manifest["files"]:
    outcome = entry["expected"]["outcome"]
    if outcome == "unspecified":
        continue
    name = entry.get("send_as", entry["name"])
    response = upload(os.path.join(directory, entry["path"]), name)
    assert response.ok == (outcome == "accept"), name

unspecified로 표시된 파일은 여기서 빠집니다. 그 답은 여러분의 정책이기 때문입니다. 정책을 정해 레시피에 expected로 적으면 반복문이 그 파일도 확인합니다. CI의 테스트 파일은 이것을 파이프라인에서 실행합니다.
