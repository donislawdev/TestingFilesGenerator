Cas d'usage

Cas de test pour l'envoi de fichiers, avec les fichiers pour les exécuter

Une liste de contrôle des cas de test d'un envoi de fichiers, de la limite de taille au nom de fichier qui tente de sortir de son dossier. Chaque cas nomme le fichier qui le teste et ce que votre système doit en faire, si bien que la liste peut être exécutée, pas seulement lue.

Toute la liste en une commande

tfg generate --preset upload-validation --limit 10mb --allow jpg,png,pdf --out ./upload écrit un fichier pour presque chaque cas ci-dessous, avec un manifeste qui dit ce qui doit arriver à chacun. Indiquez la limite et les types que déclare votre formulaire.

accept signifie que votre système doit accepter le fichier, et reject qu'il doit le refuser avec un message clair. unspecified signifie que les deux réponses peuvent être justes. Notez donc celle que votre système retient, et vérifiez qu'il s'y tient à chaque fois. Le mot qui suit le résultat est la raison donnée par le manifeste.

La limite de taille est-elle appliquée là où elle est déclarée ?

Une limite se trompe le plus souvent de deux façons : elle n'est vérifiée que dans le navigateur, ou elle est comptée en Mo là où le code compte en Mio. Le préréglage size-boundaries place un fichier à chaque distance de la limite que vous choisissez, un octet, un kilo-octet et un mégaoctet de part et d'autre.

Un fichier SVG ou HTML pris pour une image ou pour du texte brut est un moyen de faire passer un script à travers un formulaire. C'est pourquoi ils figurent dans la liste des types à refuser, sauf si votre formulaire est censé les accepter.

Un fichier qui n'a que le bon nom et la bonne taille passe tous les contrôles qui ne l'ouvrent jamais. Les fichiers d'exemple corrompus existent en PDF, Word, Excel, PowerPoint, JPG, PNG, MP4 et ZIP, et fichiers de test corrompus explique comment en fabriquer dans n'importe quel format et à n'importe quelle taille.

Nom

Le fichier revient-il sous le nom qu'on lui a donné ?

Cas de testFichierAttendu
Espaces et parenthèsesmy report (final) v2.jpgaccept
Lettres hors ASCII et un emojiwiadomość_日本語_🎉.jpgunspecified filename_invalid
Un nom de plus de 200 caractèresaaa...aaa.jpgunspecified filename_too_long

Un chemin dans un nom ne peut pas être enregistré sur un disque, donc le fichier garde un nom simple et le manifeste indique sous quel nom l'envoyer. Accepter le fichier et ne garder que la dernière partie du nom est une bonne réponse. L'écrire hors du dossier d'envoi est le défaut que ce cas existe pour trouver. Le préréglage filename-handling a bien d'autres noms : des lettres qui se ressemblent, des caractères invisibles, des noms réservés par Windows et des longueurs comptées en octets.

Dans un test

Exécuter la liste comme un test

Le manifeste contient le résultat attendu de chaque fichier et le nom sous lequel l'envoyer, donc une seule boucle exécute toute la liste : 

import json, os

directory = "upload"
manifest = json.load(open(os.path.join(directory, "manifest.json")))

for entry in manifest["files"]:
    outcome = entry["expected"]["outcome"]
    if outcome == "unspecified":
        continue
    name = entry.get("send_as", entry["name"])
    response = upload(os.path.join(directory, entry["path"]), name)
    assert response.ok == (outcome == "accept"), name

Les fichiers marqués unspecified sont laissés de côté ici, car leur réponse relève de votre propre politique. Décidez-la, écrivez-la dans la recette avec expected, et la boucle les vérifie aussi. Fichiers de test en CI exécute cela dans un pipeline.
